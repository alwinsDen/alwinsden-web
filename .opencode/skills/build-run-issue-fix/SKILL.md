# Stale iOS Pods Fix (ai-keyboard)

Fixes iOS build failures in `packages/ai-keyboard` caused by stale/broken
CocoaPods state, where an incremental `pod install` never rebuilds what moved
underneath an unchanged `Podfile.lock` (dependency paths moved — e.g. after
the nested-`node_modules` cleanup — or a dependency was swapped in place).

## Step 1 — Gather the error (always ask first)

Use the question tool to ask the user (offer options where sensible):

1. The exact build error text, or at minimum the failing file/line.
2. Whether the failing file belongs to the pod itself (its own C++/ObjC
   source under `node_modules/<pod>/...`) versus app code.

The classic symptom this skill targets: the build fails compiling a pod's
own source with `'SomePod/Sub/Path/Header.h' file not found` (e.g.
`'reanimated/CSS/utils/algorithms.h' file not found` while compiling
react-native-reanimated). If instead the error is about files under
`packages/ai-keyboard/node_modules/...`, that is the nested-node_modules
problem — point the user at the ai-keyboard AGENTS.md fix instead.

## Step 2 — Confirm the diagnosis

Verify before deleting anything:

1. Check for missing per-pod header symlink trees, while sibling pods still
   have theirs:

   ```sh
   ls packages/ai-keyboard/ios/Pods/Headers/Public/ | grep -i <podName>
   ls packages/ai-keyboard/ios/Pods/Headers/Public/<PodName>/   # expect a header_dir subfolder of symlinks
   ```

   A pod with only `*-umbrella.h` / `*.modulemap` symlinks and no mapped
   header subfolder (or the folder missing entirely) confirms staleness.
2. Cross-check the source path in
   `packages/ai-keyboard/ios/Pods/Target Support Files/<PodName>/<PodName>*.xcconfig`
   (`PODS_TARGET_SRCROOT`) and confirm the headers it points at actually
   exist.

If header symlinks are present and valid, do NOT apply this fix — diagnose
the real error instead.

## Step 3 — Choose the fix scope

Before deleting anything, use the question tool to ask the user which scope
to clean:

1. **Pods only (default/recommended)** — the standard fix below.
2. **Pods + all node_modules** — also wipe the hoisted root `node_modules`
   and any nested `packages/*/node_modules` trees, then `pnpm install`
   before rebuilding. Choose this when the header paths in the xcconfig
   point somewhere that no longer exists in `node_modules`, after any
   dependency add/remove/rename, after a pnpm version bump, or when the
   Pods-only fix already failed once.

### Option 1 — Pods only

```sh
rm -rf packages/ai-keyboard/ios/Pods packages/ai-keyboard/ios/build
pnpm dev:aikb:ios   # from repo root; re-runs pod install and the build
```

### Option 2 — Pods + all node_modules

```sh
rm -rf packages/ai-keyboard/ios/Pods packages/ai-keyboard/ios/build
rm -rf node_modules packages/*/node_modules
pnpm install
pnpm dev:aikb:ios
```

Notes for option 2:

- The repo uses `node-linker=hoisted` (see `.npmrc`), so most packages land
  in the root `node_modules`; the nested globs catch any stray per-package
  trees (e.g. a stale `packages/ai-keyboard/node_modules` that Metro/
  CocoaPods would otherwise resolve against — see the ai-keyboard AGENTS.md
  warning).
- Do NOT delete a nested `packages/ai-keyboard/node_modules` and then run
  npm/npx inside `packages/ai-keyboard` to "reinstall" — always reinstall
  via `pnpm install` from the repo root.

If the `ios/` directory itself looks wrong (missing files, broken project,
suspicious Podfile), regenerate it fully first:

```sh
pnpm --filter ai-keyboard exec expo prebuild --platform ios --clean
pnpm dev:aikb:ios
```

## Notes

- `ios/` is gitignored and fully generated by prebuild, so deleting
  `Pods`/`build` (or regenerating `ios/`) loses nothing.
- `pnpm dev:aikb:ios` alone is NOT enough to repair a stale `Pods` tree:
  CocoaPods sees an unchanged `Podfile.lock` and skips regeneration. The
  delete in Step 3 is the essential part.
- A full clean rebuild takes a while; wiping `node_modules` too makes it
  noticeably longer (full pnpm store re-link + pod re-install). Warn the
  user before starting either option.
